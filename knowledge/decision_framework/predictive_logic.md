# Predictive Logic（预测型决策逻辑）

> **用途**：预测型 / 瀑布项目情境题的识别信号、决策原则与标准处理顺序。供 Agent 在 `project_type = predictive` 时调用。
>
> **调用时机**：Step 1 判定为 Predictive，或 Hybrid 题中当前动作属于预测型治理侧（基准、CCB、变更日志）。

---

## 1. 判定为预测型项目的条件

满足以下**任一强信号**即可倾向 Predictive；出现 2 项以上高置信判定：

| 信号类型 | 关键词 / 场景线索 |
|----------|-------------------|
| 计划与基准 | WBS、甘特图、里程碑、进度基准、成本基准、范围基准、绩效测量基准（PMB） |
| 变更治理 | 变更控制委员会（CCB）、变更请求、变更日志、配置管理、书面批准 |
| 文档驱动 | 项目管理计划、子管理计划、项目章程、工作绩效数据/信息/报告 |
| 阶段门 | 阶段收尾、阶段关口、go/no-go、瀑布、sequential phases |
| 合同与采购 | 固定总价合同（FFP）、招标文件、卖方建议书、合同谈判（非迭代交付语境） |
| 绩效分析 | 挣值管理（EVM）、SV/CV/SPI/CPI、偏差分析、趋势分析、完工估算（EAC） |

**排除信号**（出现则改判 Agile 或 Hybrid）：

- Sprint、迭代、Product Backlog、Scrum Master、每日站会
- 用户故事、燃尽图、增量交付、持续集成

**Hybrid 处理**：同时出现「基准/CCB」与「Sprint/Backlog」→ 标注 Hybrid；**先判断题目问的是哪一侧动作**（计划变更走 Predictive 逻辑，迭代内调整走 Agile 逻辑）。

## 2. 高频关键词 → 决策指向

| 关键词 | 通常指向的过程 / 动作 |
|--------|------------------------|
| charter / 章程 | Initiating；章程由发起人批准，PM 可参与制定但通常无权单独修改 |
| baseline / 基准 | 变更前须走变更控制；未经批准不得随意修改基准 |
| change request / 变更请求 | 记录 → 评估影响 → CCB 审批 → 更新计划/文件 → 通知相关方 |
| work performance data | Executing 中产生；需经分析成为 information |
| variance / 偏差 | Monitoring and Controlling；先分析原因再决定纠正/预防 |
| risk register / 风险登记册 | 已识别风险；新问题可能是 issue，不是 risk |
| issue / 问题 | 已发生；登记问题日志，分配责任人，跟踪关闭 |
| stakeholder register / 相关方登记册 | 识别 → 分析 → 制定参与策略 |
| lessons learned / 经验教训 | 全周期收集；Closing 时归档，不只收尾才做 |
| RFI / RFP / 合同 | Procurement；遵循采购管理计划与合同条款 |
| quality audit / 质量审计 | 过程是否符合计划与标准 |
| inspection / 检查 | 可交付成果是否符合验收标准 |

**否定词陷阱**：`NOT`、`EXCEPT`、`LEAST likely`、`FIRST`（≠ `BEST`）— 必须回读题干问法。

## 3. 项目经理决策原则（Predictive）

按优先级应用，**高优先级覆盖低优先级**：

```
P1  Analysis before action      → 先收集事实、评估影响，再采取行动
P2  Collaborate before escalate → 先与团队/相关方沟通协商，再上报发起人/管理层
P3  Follow process before changing → 先走变更/风险/问题流程，再执行变更
P4  Update plan before execution → 基准或计划更新获批后，再指导执行
P5  Document and communicate    → 关键决策留痕，通知受影响相关方
```

### 角色边界速查

| 角色 | Predictive 下典型职责 |
|------|------------------------|
| PM | 整合、协调、执行计划、提出变更、管理相关方期望 |
| Sponsor / 发起人 | 批准章程、批准重大变更、提供资金、解决超出 PM 权限的问题 |
| CCB | 审查变更请求，批准/驳回/推迟 |
| 团队 | 提供估算、执行工作、参与风险识别 |
| 职能经理 | 提供资源、技术权威（矩阵环境） |

**PM 不应**：未经 CCB 改基准；替发起人签章程；忽略合同条款自行让步。

## 4. 变更处理逻辑

标准顺序（考试问 **First / Next** 时逐步匹配）：

```
1. 识别变更触发（请求、缺陷、事件、政府法规等）
2. 记录变更请求（书面）
3. 评估对范围/进度/成本/质量/风险/资源的影响
4. 制定备选方案与推荐方案
5. 提交 CCB（或授权人）审批
6. 批准 → 更新项目管理计划及组件、基准、项目文件
7. 通知相关方
8. 执行已批准的变更
9. 监控变更实施效果
```

| 问法 | 正确答案倾向 |
|------|--------------|
| **First** | 记录变更请求 + 评估影响（分析），而非立即执行 |
| **Next** | 看上一动作：已记录未评估 → 评估；已批准未更新 → 更新计划 |
| **Best** | 完整变更控制流程 + 相关方沟通，可能包含预防再发 |
| 范围蔓延（无正式变更） | 拒绝执行或走变更流程，**不**默认接受 |

**陷阱**：把「执行变更」当作第一步；把「拒绝所有变更」当作最佳（应评估后决策）。

## 5. 风险处理逻辑

区分 **Risk（未发生）** vs **Issue（已发生）**：

| 状态 | 登记位置 | 首要动作 |
|------|----------|----------|
| 潜在事件 | 风险登记册 | 分析 → 规划应对（规避/转移/减轻/接受）→ 实施应对 → 监督 |
| 已发生 | 问题日志 | 记录 → 分配责任人 → 纠正/应急 → 跟踪关闭 |

**风险应对策略选择信号**：

| 策略 | 适用信号 |
|------|----------|
| Avoid / 规避 | 消除威胁，改计划 |
| Transfer / 转移 | 保险、合同、担保（通常付代价） |
| Mitigate / 减轻 | 降低概率或影响 |
| Accept / 接受 | 影响小或成本过高；主动接受需建立储备 |
| Exploit / 提高 | 机会 — 确保实现 |
| Share / 分享 | 机会 — 与第三方合作分成 |

**First 题默认路径**：新风险 → 更新风险登记册 → 定性/定量分析 → 规划应对（不是立刻上报，除非超出权限且已尝试协作）。

**升级条件**：威胁重大、超出 PM 权限、需要组织级资源或战略决策 → 在分析并与关键相关方沟通后上报发起人。

## 6. 干系人（相关方）问题处理逻辑

```
1. 查阅相关方登记册与参与计划
2. 理解诉求、影响力和紧迫性
3. 面对面或正式沟通（非仅邮件轰炸）
4. 协商、影响、解决冲突（合作/妥协视情境）
5. 更新相关方参与计划 / 登记册
6. 持续监督参与效果
```

| 情境 | 优先动作 |
|------|----------|
| 相关方抵制 | 了解原因 → 沟通 → 调整参与策略（非忽视或强制） |
| 冲突（团队内部） | 合作解决问题 / 面对面沟通（非首先上报发起人） |
| 期望不合理 | 管理期望、澄清范围与约束，引用章程/计划 |
| 高层施压改范围 | 走变更流程，非口头答应 |
| 沟通不足 | 检查沟通管理计划，选择合适技术与频率 |

**People 领域铁律**：相关方问题 ≠ 技术问题；**先沟通，再改计划或升级**。

## 7. 常见考试陷阱（Predictive）

| 陷阱 | 错误倾向 | 正确倾向 |
|------|----------|----------|
| 跳过分析 | 立即执行、立即拒绝、立即上报 | 先记录、评估、分析 |
| 过度升级 | 第一步找发起人/管理层 | 先团队/相关方协作 |
| First vs Best 混淆 | 选长期最优解 | First 选流程第一步 |
| 基准随意改 | PM 直接调进度/成本基准 | 走 CCB / 变更控制 |
| Risk vs Issue | 已发生仍写进风险登记册当风险管 | 已发生 → 问题日志 |
| 范围蔓延 | 客户口头加活就做 | 变更请求或正式评估 |
| 镀金 | 主动加功能讨好客户 | 按批准范围交付 |
| 章程 vs 计划 | 混淆批准人与内容 | 章程=发起人批准；计划=PM 制定 |
| 经验教训 | 只在收尾才记录 | 全周期收集 |
| 合同情境 | 忽略合同只讲「友好协商」 | 合同条款 + 采购流程优先 |
| 矩阵环境 | 越权指挥职能经理的人 | 协商、影响、升级职能经理 |
| 绝对化选项 | 选 always / never / immediately | 怀疑极端措辞 |

## 8. Agent 调用检查清单

分析 Predictive 情境题时，依次确认：

- [ ] 强信号是否支持 Predictive（非 Agile 误判）
- [ ] 项目阶段是否明确（决定可用过程）
- [ ] 问法是 First / Next / Best / Most Appropriate
- [ ] 适用 P1–P4 哪条原则
- [ ] 问题是变更 / 风险 / 问题 / 相关方 / 质量 / 采购哪一类
- [ ] 选项是否触犯 §7 陷阱
